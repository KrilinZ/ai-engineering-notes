GitHub Pages: How to Publish a Static Site for Free in 2026

What is GitHub Pages, and why does every beginner developer end up using it? It is the free static site hosting service built into GitHub, which lets you publish HTML, CSS, and JavaScript files directly from a repository. Every GitHub account gets hosting at `username.github.io`, with automatic HTTPS, support for custom domains, and built-in builds through Jekyll or GitHub Actions. It is designed for portfolios, documentation, and personal projects — not for server-side applications.

If you are learning to code, GitHub Pages is usually the first place your work goes live on the internet. There is no credit card, no server to configure, and no deployment pipeline to build from scratch. This article explains what GitHub Pages is, how to publish your first site step by step, what its limits are in 2026, and when you should consider alternatives.

What is GitHub Pages and how does it work?

GitHub Pages is a static hosting service that GitHub offers for free to every user, organization, and public repository. According to GitHub Docs in 2026, it serves files straight from a Git repository, which means your website is versioned, reviewable, and deployable with a simple `git push`. There is no backend: the service only delivers static assets like HTML, CSS, JavaScript, and images.

There are three types of sites. A user site lives in a repository named `username.github.io` and is served at that exact address. An organization site works the same way but for an organization account. A project site lives inside any other repository and is served at `username.github.io/repository-name`. Under the hood, GitHub Pages runs on a CDN (content delivery network, a distributed system of servers that caches your files close to visitors) so pages load fast worldwide.

The stack is intentionally simple. You write files in Markdown or plain HTML, commit them to your repository, and GitHub builds and publishes the result. If you want automation, GitHub Actions is GitHub's built-in CI/CD tool that can compile your site on every push, which is now the recommended deployment workflow according to GitHub's changelog announcement in 2022 and remains the standard approach in 2026.

Is GitHub Pages really free?

Yes, GitHub Pages is free for public repositories, with published usage limits. According to GitHub Docs in 2026, published GitHub Pages sites have a soft limit of 1 GB repository size and a monthly bandwidth allowance of 100 GB, and builds are capped at 10 per hour. For a portfolio or documentation site, those limits are generous: 100 GB of bandwidth per month is far more traffic than most personal sites ever receive.

One important detail: private repositories with Pages require a paid plan. According to GitHub's pricing documentation in 2026, publishing a GitHub Pages site from a private repository is available on GitHub Pro, Team, and Enterprise plans, while free accounts can only publish from public repositories. If you are a student, the GitHub Student Developer Pack includes GitHub Pro at no cost, which is worth checking before you pay.

GitHub's terms also restrict commercial use. According to GitHub's Terms of Service in 2026, GitHub Pages is not intended for commercial transactions, paid advertising, or serving as a backend for a business application. A portfolio that lands you freelance work is fine; running an online store from Pages is not.

How do you publish your first site on GitHub Pages?

Publishing takes about ten minutes. First, create a new repository on GitHub. If you want your site at the root address `username.github.io`, name the repository exactly that. For a project site, any repository name works.

Second, add an `index.html` file to the repository. This is the entry point browsers look for. A minimal version looks like this:

```html My first site

Hello, world

```

Third, open the repository's Settings tab and find the Pages section. Under "Build and deployment," choose "Deploy from a branch" and select the `main` branch with the root (`/`) folder. GitHub will build the site and show you the live URL, usually ready within a minute or two.

Fourth, commit and push any changes. Every push to the selected branch triggers a rebuild. If you prefer the modern approach, select "GitHub Actions" as the source instead, and GitHub will generate a starter workflow that builds and deploys your site automatically. This is the flow GitHub recommends for Jekyll and custom build tools as of 2026.

How do custom domains and HTTPS work on GitHub Pages?

A custom domain is your own web address, like `yourname.dev`, instead of `username.github.io`. GitHub Pages supports this natively. In your repository's Pages settings, enter your domain in the "Custom domain" field, and GitHub creates a `CNAME` file in your repository, which is a plain text file containing your domain name.

On your DNS provider's side, you configure the records. For an apex domain (the bare domain without `www`), GitHub Docs in 2026 recommends creating `A` records pointing to GitHub's IP addresses, or an `ALIAS`/`ANAME` record if your provider supports it. For a subdomain like `www`, a single `CNAME` record pointing to `username.github.io` is enough. DNS propagation can take from a few minutes to 48 hours depending on your provider.

Once the domain resolves, enable "Enforce HTTPS" in the Pages settings. GitHub provisions a free TLS certificate through Let's Encrypt, so your custom domain gets the same HTTPS encryption as the default URL. GitHub also supports domain verification in 2026, which lets you prove ownership and prevents other users from taking over your domain on their own accounts, a protection GitHub recommends for all custom domains.

How do Jekyll and GitHub Actions fit in?

Jekyll is a static site generator written in Ruby that transforms Markdown files and templates into a complete static website. GitHub Pages has native Jekyll support: if your repository contains Markdown files with Front Matter (a metadata block at the top of a file delimited by `---`), GitHub builds the site automatically without any configuration from you. This is why Jekyll remains the default engine for GitHub Pages in 2026.

The typical Jekyll workflow looks like this: you write posts as Markdown files in a `_posts` folder, define layouts in a `_layouts` folder, and Jekyll compiles everything into HTML on every push. Themes are installable through the `_config.yml` file, so you can have a decent-looking blog without writing CSS.

For anything beyond plain Jekyll, GitHub Actions is the tool to use. A workflow file in `.github/workflows/` can install Node.js, run a build with a framework like Astro or Hugo, and deploy the output folder to Pages. GitHub's official documentation in 2026 provides ready-made starter workflows for the most common static generators, so setting this up is usually a copy-paste-and-commit job. When is GitHub Pages not enough?

GitHub Pages only serves static files. There is no server-side code, no database, no user authentication, and no form processing out of the box. You can work around some of this with third-party services: forms can post to a service like Formspree, search can run client-side, and comments can be embedded via an external provider. But if your project needs a backend, Pages is the wrong tool.

The common alternatives in 2026 are Netlify, Vercel, and Cloudflare Pages. All three offer free tiers for static sites with features GitHub Pages lacks: serverless functions, preview deployments for pull requests, and redirect/rewrite rules. According to each platform's documentation in 2026, their free tiers are suitable for personal projects, with paid plans for teams and higher traffic.

A practical rule of thumb: start on GitHub Pages while you are learning, because it teaches you Git-based deployment with zero complexity. Migrate when you need dynamic functionality, build previews, or finer control over caching and headers. Migrating is usually painless since all these platforms deploy from the same Git repositories.

What are the most common GitHub Pages mistakes?

The most frequent mistake is a 404 error right after publishing. This usually means there is no `index.html` at the root of the published branch, or the site is still building. Check the Pages settings for the deployment status, and confirm your entry file exists with the exact lowercase name `index.html`.

The second classic error is broken images and links caused by absolute paths. A path like `/images/photo.png` works on `username.github.io` but breaks on a project site served from `username.github.io/repo-name`, because the leading slash points to the domain root. Use relative paths (`images/photo.png`) or prefix paths with the repository name to make your site work in both contexts.

Third, failed builds with Jekyll. If your Markdown has malformed Front Matter or a plugin that GitHub Pages does not support, the build fails silently and the old version stays live. Build your site locally with `bundle exec jekyll serve` to reproduce the error, and remember that GitHub Pages only supports a whitelist of Jekyll plugins according to GitHub Docs in 2026.

Finally, caching frustration: after a push, your browser may show the old version for several minutes. Hard-refresh with `Ctrl+Shift+R` (or `Cmd+Shift+R` on Mac) before assuming something is broken.

Closing: your first deploy is one push away

GitHub Pages removes every excuse for not having a live portfolio. Create a repository, commit an `index.html`, flip the setting, and your work is publicly reachable with HTTPS in minutes. From there, add a custom domain, experiment with Jekyll or a GitHub Actions workflow, and treat every project as a deployable artifact. Recruiters in 2026 consistently value candidates who can show deployed work, not just code sitting in a repository, so publish early and publish often.
