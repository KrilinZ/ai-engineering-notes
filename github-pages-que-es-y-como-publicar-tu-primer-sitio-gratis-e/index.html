GitHub Pages: qué es y cómo publicar tu primer sitio gratis en 2026

¿Qué es GitHub Pages y por qué debería importarte si estás empezando en desarrollo? Es un servicio gratuito de GitHub que publica sitios web estáticos directamente desde un repositorio, sin servidores que configurar ni costes de hosting. Escribes tu HTML, CSS y JavaScript (o usas un generador como Jekyll), haces push a una rama y GitHub compila y sirve tu web en una URL del tipo `usuario.github.io`, con HTTPS incluido.

Si estás dando tus primeros pasos, probablemente ya hayas terminado algunos proyectos y te preguntes dónde mostrarlos. Un repositorio lleno de código no impresiona a nadie que no lo abra; una URL que funciona en dos clics, sí. GitHub Pages resuelve exactamente ese problema, y en este artículo verás qué es, cómo funciona por dentro, cómo publicar tu primer sitio paso a paso, cómo conectar un dominio propio y cuándo conviene elegirlo frente a alternativas como Netlify, Vercel o Cloudflare Pages.

¿Qué es GitHub Pages y cómo funciona?

GitHub Pages es un servicio de hosting estático integrado en GitHub que convierte el contenido de un repositorio en un sitio web publicado. En esencia, funciona como un pipeline de despliegue automático: cada vez que haces push a la rama configurada (normalmente `main`), GitHub ejecuta un proceso de build y publica el resultado en una URL pública.

El flujo interno tiene tres piezas. Primero, el origen: tu repositorio, que puede contener HTML plano o archivos fuente de un generador de sitios estáticos como Jekyll, que es el generador integrado por defecto en GitHub Pages (Jekyll es un generador escrito en Ruby que convierte archivos Markdown y plantillas Liquid en HTML estático). Segundo, el build: GitHub ejecuta la compilación mediante GitHub Actions, su plataforma de automatización de flujos de trabajo, usando el workflow oficial `actions/deploy-pages` recomendado en la documentación de GitHub. Tercero, la publicación: el sitio se sirve desde la infraestructura de GitHub con CDN (red de distribución de contenido que acerca los archivos al usuario final) y certificado HTTPS automático.

Existen dos tipos de sitio: el sitio de usuario u organización (`usuario.github.io`, uno por cuenta, que sirve de raíz de tu portfolio) y los sitios de proyecto (uno por repositorio, publicados en `usuario.github.io/nombre-del-repo`). Esta distinción importa al estructurar tu portfolio: la raíz suele ser la landing personal y cada proyecto vive en su propio repositorio con su propia URL. Así, quien visite tu perfil puede navegar de tu presentación general al código fuente de cada proyecto sin salir de tu ecosistema.

¿GitHub Pages es gratis de verdad? Límites y planes

¿Es GitHub Pages realmente gratuito? Sí, es gratuito para repositorios públicos en cuentas personales, sin necesidad de plan de pago. GitHub lo ofrece como parte del servicio a todos los usuarios, incluidos los de la capa gratuita. Ahora bien, "gratis" no significa "sin límites", y conviene conocerlos antes de comprometer tu proyecto a largo plazo.

Según la documentación oficial de GitHub (consultada en 2026), la recomendación es mantener el sitio publicado por debajo de 1 GB de tamaño, y el ancho de banda tiene un soft limit mensual de 100 GB por sitio. Un soft limit significa que no hay un corte automático: si superas el límite de ancho de banda, GitHub te enviará un aviso por correo para que reduzcas el consumo, por ejemplo optimizando imágenes, comprimiendo assets o usando un CDN externo delante de tu sitio. Para un portfolio o un blog técnico, estos límites son más que generosos; solo entran en juego con sitios de tráfico masivo o repositorios con archivos pesados sin optimizar.

Hay una restricción de uso importante: GitHub Pages está pensado para sitios estáticos, no para aplicaciones con backend. No puedes ejecutar código de servidor (Node, PHP o Python en runtime), ni bases de datos, ni autenticación propia del servidor. Para lógica dinámica, el patrón habitual es combinar Pages con APIs externas o servicios serverless que sí ejecuten esa parte. Y si trabajas en una empresa, ten en cuenta que GitHub Pages en cuentas de organización con planes de pago permite publicar desde repositorios privados, una opción que no existe en la capa gratuita personal.

Cómo publicar tu primer sitio en GitHub Pages paso a paso

¿Cuánto se tarda en publicar un sitio en GitHub Pages? Menos de quince minutos si ya tienes el código listo. El camino más simple es con HTML estático puro, y es el que te recomiendo para entender el mecanismo antes de añadir herramientas.

Primero, crea un repositorio llamado exactamente `tuusuario.github.io`, sustituyendo "tuusuario" por tu nombre de usuario de GitHub. Ese nombre especial activa el sitio raíz de tu cuenta. Segundo, sube un archivo `index.html` en la raíz del repositorio: puede ser una landing mínima con tu nombre, una frase sobre lo que haces y enlaces a tus proyectos. Tercero, ve a Settings → Pages en el repositorio y selecciona la rama `main` como fuente de despliegue (con el workflow clásico) o, si usas el flujo moderno, elige la opción de GitHub Actions que GitHub sugiere automáticamente. Cuarto, espera uno o dos minutos: GitHub ejecutará el build y tu web estará viva en `https://tuusuario.github.io`.

Si en lugar de HTML plano usas Jekyll, el proceso es casi idéntico: GitHub detecta los archivos de configuración y compila automáticamente en cada push. Para frameworks como Astro, Hugo o Next.js en modo estático, el patrón recomendado por GitHub es un workflow de GitHub Actions que instala dependencias, ejecuta el build y despliega con los actions oficiales (`actions/upload-pages-artifact` y `actions/deploy-pages`). Un detalle que atrapa a muchos principiantes: las rutas relativas. En un sitio de proyecto (`usuario.github.io/repo`), una ruta absoluta como `/imagen.png` romperá la carga, porque el navegador la buscará en la raíz del dominio y no dentro de la carpeta del repositorio; usa rutas relativas (`./imagen.png`) o configura la URL base correctamente en tu framework.

GitHub Pages con dominio propio y HTTPS

¿Puedes conectar tu propio dominio a GitHub Pages? Sí, y el certificado HTTPS se gestiona automáticamente. GitHub utiliza Let's Encrypt, la autoridad de certificación gratuita sin ánimo de lucro, para emitir y renovar certificados de forma automática en los dominios personalizados, una funcionalidad plenamente operativa según la documentación de GitHub en 2026.

La configuración tiene dos lados. En GitHub: añade tu dominio en Settings → Pages del repositorio y activa la casilla "Enforce HTTPS" una vez el certificado esté aprovisionado (puede tardar desde minutos hasta un día). En tu registrador de dominios: crea un registro DNS de tipo `A` apuntando a las direcciones IP que GitHub documenta para Pages, o un registro `CNAME` si usas un subdominio como `www.tudominio.com`. GitHub también admite la verificación de dominio para prevenir el "takeover" de dominios, un ataque en el que alguien reclama tu dominio si lo desvinculas sin soltar antes el registro DNS. Verificar el dominio cuesta dos minutos y elimina ese riesgo.

¿Merece la pena el dominio propio para un portfolio? En mi experiencia revisando portfolios de candidatos junior, sí: una URL memorable en tu CV (`maria-garcia.dev`) transmite más cuidado profesional que una URL genérica de `github.io`, y cuesta el precio anual de un dominio, no el de un hosting. Además, el dominio te pertenece: si mañana migras a otra plataforma, tus enlaces y tu posicionamiento te acompañan.

¿Cuándo usar GitHub Pages y cuándo no? Alternativas

¿Cuándo conviene GitHub Pages y cuándo mirar otras opciones? Usa GitHub Pages cuando publiques sitios estáticos, documentación, portfolios o blogs personales, y considera alternativas cuando necesites previews por pull request, funciones serverless o builds más complejos. Es la regla práctica que mejor resume la decisión.

GitHub Pages brilla en tres escenarios: portfolios y CVs técnicos, documentación de proyectos open source (es el estándar de facto en el ecosistema GitHub) y blogs personales con generadores estáticos. Sus puntos débiles son igual de claros: no hay previews de despliegue por pull request (Netlify y Vercel las ofrecen de serie), no hay funciones serverless nativas, el soft limit de ancho de banda puede apretar en sitios con mucho tráfico y el ecosistema de plugins de Jekyll está más restringido que el de otras plataformas.

Las alternativas principales en 2026 son tres. Netlify ofrece despliegue continuo desde Git, previews por PR, funciones serverless y un plan gratuito cómodo; es la opción más directa si quieres cero fricción. Vercel, creada por los desarrolladores de Next.js, es la elección natural si tu stack es ese framework, con optimizaciones de rendimiento automáticas. Cloudflare Pages destaca por servir tu sitio desde la red CDN global de Cloudflare con límites de build muy amplios en su plan gratuito. Todas son gratuitas para uso personal, así que la decisión se basa en tu stack y en las funciones que necesites, no en el precio. Para un primer portfolio, GitHub Pages es perfectamente suficiente; migra después si creces.

GitHub Pages para tu portfolio técnico: cómo convertirlo en puerta de entrada laboral

¿Cómo conviertes un sitio estático en una puerta de entrada laboral? Un portfolio en GitHub Pages funciona cuando cada proyecto cuenta una historia completa: problema, solución, decisiones técnicas y resultado, no solo una captura de pantalla. Los reclutadores técnicos dedican pocos minutos por candidato, y tu web debe permitirles entender tu criterio en ese tiempo.

Estructura que funciona: una landing con quién eres y qué tecnologías dominas, una sección de proyectos donde cada uno enlace al repositorio y a la demo desplegada, y un blog técnico donde documentes lo que aprendes. Ese blog es más valioso de lo que parece: escribir sobre lo que estudias consolida el conocimiento y demuestra comunicación, una habilidad que los equipos valoran tanto como el código. Y en un mercado donde la IA está transformando cómo se trabaja, saber usarla con criterio marca la diferencia: el programa de ai fluency de 4Geeks está pensado precisamente para ese perfil profesional que necesita hablar el idioma de la IA con soltura, y si tu punto de partida es más básico, aprender inteligencia artificial desde cero es el camino, y la guía de ai fluency encaja bien como primer paso antes de especializarte.

Dos consejos finales de ejecución. Primero, mide: añade una herramienta de analítica (Google Analytics o Plausible) para saber qué proyectos miran los visitantes y priorizar en consecuencia. Segundo, mantén vivo el sitio: un portfolio cuya última entrada tiene dos años comunica abandono. Un commit mensual, aunque sea pequeño, mantiene la señal de actividad que reclutadores y bots detectan.

Preguntas frecuentes

¿GitHub Pages es gratis para siempre?

Sí, GitHub Pages es gratuito para repositorios públicos en cuentas personales, y GitHub no ha anunciado cambios en ese modelo según su documentación vigente en 2026. Los límites de tamaño y ancho de banda aplican igualmente, y el uso comercial generalizado está desaconsejado en los términos del servicio. Para usos personales, portfolios y documentación, no hay coste.

¿Se puede usar GitHub Pages con React o Next.js?

Sí, pero solo en modo estático: GitHub Pages no ejecuta código de servidor, así que frameworks como React, Vue o Next.js funcionan si generan HTML estático en el build. Next.js debe configurarse con `output: 'export'`. Las funciones de servidor, la renderización en runtime y las rutas de API no están soportadas; para eso, Vercel o Netlify son opciones más adecuadas.

¿Cuál es el límite de tamaño de GitHub Pages?

Según la documentación oficial de GitHub, el sitio publicado debe mantenerse por debajo de 1 GB de tamaño recomendado, y el repositorio fuente está sujeto a los límites generales de repositorio de GitHub. El ancho de banda tiene un soft limit mensual de 100 GB por sitio, con aviso por correo si lo superas.

¿GitHub Pages soporta HTTPS en dominios propios?

Sí, GitHub emite y renueva automáticamente certificados de Let's Encrypt para dominios personalizados, con la opción "Enforce HTTPS" en la configuración del repositorio. El aprovisionamiento del certificado puede tardar hasta 24 horas tras configurar el DNS correctamente. Los subdominios y dominios apex están ambos soportados.

¿Puedo usar GitHub Pages para un blog?

Sí, es uno de sus usos más habituales. Con Jekyll (integrado por defecto) o generadores como Hugo o Astro, publicas artículos en Markdown que GitHub compila automáticamente en cada push. Es la solución estándar para blogs técnicos de desarrolladores, con la ventaja de que el blog y el código viven en el mismo lugar.

¿Qué diferencia hay entre GitHub Pages y Netlify?

La diferencia clave está en las funciones de plataforma: Netlify ofrece previews por pull request, funciones serverless, formularios gestionados y redirecciones más flexibles, mientras que GitHub Pages es más simple pero está integrado nativamente en GitHub sin configuración adicional. Para sitios estáticos básicos, ambos son gratuitos y equivalentes en resultado; para proyectos con más complejidad, Netlify suele dar más margen.
